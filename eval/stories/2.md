# the whole web client

Build the web client of the Shared Equipment Checkout service in `app/web/` so that the exam
passes: 22 browser rows that measure the page in Chromium with every API call faked, and 30
journey rows that drive it in Chromium against the real API and database.

## What exists and is not yours to change

`app/api/` is built and merged (story 1): the HTTP API of `docs/TECH-SPEC.md` section 12.3, the
database and the seeded users Ada Admin (1), Mia Member (2) and Sam Member (3). Your client talks
to it and to nothing else. You change no file under `app/api/`, and nothing under `eval/`,
`docs/` or `.github/`.

The Compose stack, the images and the nginx proxy of the real deployment are story 3, not yours.
For this story the exam brings its own stack (`eval/stack/compose.yml`) and builds your client
into it, so you write no Dockerfile, no nginx configuration and no compose file.

## Your files

Everything the client is, under `app/web/`: `package.json`, `package-lock.json`, `index.html`,
`vite.config.js`, and the source under `app/web/src/`. Static files, if you need any, go under
`app/web/public/`. `eval/stories/2.txt` lists exactly what you may change; a path outside it fails
the gate. `app/web/Dockerfile`, `app/web/nginx.conf` and `app/web/.dockerignore` belong to
story 3: do not create them.

Commit `package-lock.json`. The exam installs with `npm ci`, which refuses to run without it.

## The contract, pinned

- **`docs/TECH-SPEC.md` 12.7** the entry points (`app/web/index.html` with `<div id="root">`,
  `src/main.jsx` mounting `src/App.jsx`, whose default export `App` takes no props), the calls
  (global `fetch`, looked up at each call; `X-User-Id` on every call; success is exactly status
  200), the name check before an Add, the state demos, an Add made from the Show empty list view,
  and a failed list fetch.
- **12.8** every `data-testid`, the fifteen icon buttons and their `title` and `aria-label`, the
  control inventory (nothing else may be focusable or clickable), and the four modals.
- **12.9** every on-screen string, exactly, including "–" as U+2013 and "…" as U+2026, and the
  system font stack.
- **12.10** the versions: Node.js 22, React 18.3, Vite 5.4 with `@vitejs/plugin-react` 4,
  JavaScript and not TypeScript.
- **`docs/PRD.md`** the requirements REQ-001 to REQ-017 and their criteria; section 4 defines the
  words the criteria use. The rows grade what the PRD asks, not only what a row happens to touch:
  where a row and the PRD seem to disagree, report it in your handoff note.
- **`docs/mockup.html`** the look the REQ-015 rows measure: 48px rows of equal height, pill
  badges, round icon buttons, a sticky top bar blurring what is behind it by 20px, 12px card
  corners, 16px modal corners, 8px on the switcher and the Add field, 10px on member buttons.
  Open it in a browser. Where the PRD or a decision differs from the mockup (12.9 names each
  case), the PRD wins.

## The exam, and how to run it

From the repository root: `sh eval/run.sh`. It needs Docker with Compose v2, Node.js 22 and
Python 3.12. It runs three groups of rows, each whatever happened to the one before:

1. **The API rows** (`eval/api/`), as in story 1. They must still pass; you do not touch the API.
2. **The browser rows** (`eval/web/tests/browser/`). The exam builds your `app/web` for
   production inside a container: `npm ci`, then `vite build` with `VITE_API_BASE_URL=/api`,
   then serves the result with nginx (`eval/stack/compose.yml` and `eval/stack/nginx.conf` show
   exactly how). Playwright opens it in Chromium and answers every `/api` request itself
   (`eval/web/tests/browser/_fake-api.js`), so these rows judge the page alone: layout, computed
   styles, keyboard operation and the control inventory.
3. **The journey rows** (`eval/e2e/`) against the same stack, now with the real API and
   PostgreSQL behind nginx's `/api`. Two browser contexts at once, requests rewritten in flight to
   force refused and rejected actions, and three production rows at the end that stop and restart
   the stack and check that what was committed is still there and the users were seeded once.

Nothing you write runs on the machine that holds the exam: your install scripts and your build run
inside the container. The reports land in `eval/reports/` (`api.xml`, `browser.xml`,
`journey.xml`), one case per row, the row id opening each case's name. The run ends with the row
check: every id in `eval/api/rows.txt`, `eval/web/rows.txt` and `eval/e2e/rows.txt` needs a
passing case. A missing, failed, errored or skipped case fails it, and the check names each one.
What each row checks is in `docs/eval-plan.md` section 3, under its requirement. Playwright keeps
a trace of every case under `eval/reports/`; open one with
`eval/web/node_modules/.bin/playwright show-trace <file>`.

The production rows run only when every journey row has passed (Playwright runs them as a
dependent project). Until then they are reported as skipped, and the row check counts them as
failing.
