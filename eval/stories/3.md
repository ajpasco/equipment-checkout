# the Compose stack and the journey

Build the stack that runs the Shared Equipment Checkout service, in `app/`, so that the exam
passes: 30 journey rows that drive the whole application in Chromium against your stack, with
the real API and PostgreSQL behind your nginx, including three production rows that stop and
restart it.

## What exists and is not yours to change

`app/api/` (story 1) and `app/web/` (story 2) are built and merged, and every API and browser row
passes against them. You change no file in either beyond the five named below, and nothing under
`eval/`, `docs/` or `.github/`. If the stack cannot work without a change to the API or the
client, stop and say so in your handoff note; do not make the change.

## Your files

`eval/stories/3.txt` lists exactly what you may change; a path outside it fails the gate.

- `app/compose.yml`: the stack, three services `db`, `api` and `web`.
- `app/.env.example`: every setting the stack reads, with placeholders only.
- `app/api/Dockerfile` and `app/api/.dockerignore`: the API's image.
- `app/web/Dockerfile`, `app/web/nginx.conf` and `app/web/.dockerignore`: the client's production
  build, served by nginx, which sends `/api` to the API.

## The contract, pinned in `docs/TECH-SPEC.md`

- **Section 1** the three services: `db` is PostgreSQL, `api` the FastAPI application
  (`uvicorn app.main:app`), `web` nginx serving the static build of `app/web` and proxying `/api`
  to `api`. The browser reaches the API only through that same origin.
- **Section 6** the settings. The API reads only `DATABASE_URL`. The `db` container takes
  `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB`. `WEB_PORT` is the published port of
  `web`, default `8080`. `VITE_API_BASE_URL` is a build value of the client, default `/api`. The
  API listens on port 8000 inside the Compose network and is not published; the database is not
  published. `.env.example` is committed with placeholders and `.env` is git-ignored.
- **Section 7** persistence: PostgreSQL's data directory is a named volume, so
  `docker compose down` without `-v` keeps every committed change and `down -v` is a first start.
- **Section 5.1** no health route exists. The `api` health check calls `GET /api/users` with the
  header `X-User-Id: 1`. **Section 5.4** the server's own access log is off, so the application's
  `app.access` line is the only request log.
- **Section 12.10** the versions: `postgres:16`, `nginx:1.27-alpine`, Python 3.12, Node.js 22.
- **Section 13.1** the containers line: the API runs as a non-root user; the defaults proposed
  there (pinned base images, non-root `api` and `web`, no secret baked into an image, a
  `.dockerignore` that excludes tests, `.env` and version control) are what to build to.
- **Section 14** the conventions, and the tools the exam's conventions step runs.

How the settings reach the stack: every value comes from the env file Compose is given, by
interpolation in `app/compose.yml` (`${POSTGRES_USER}` and so on). The exam passes
`eval/e2e/eval.env` with `--env-file`; on your own machine Compose reads `app/.env`, copied from
`app/.env.example`. Do not use `env_file:`.

## What the exam will start

Your stack's containers run on the machine that holds the exam, beside the gate. Before anything
starts, `eval/check_compose.py` reads `app/compose.yml` as Compose resolves it and refuses the
stack unless every part of it is one an ordinary three-service stack needs. Allowed: images built
from a context and a Dockerfile inside `app/`, with `args` and `target`; `image`, `command`,
`entrypoint`, `environment`, `ports`, `expose`, `depends_on`, `healthcheck`, `restart`, `user`,
`working_dir`, `init`, `read_only`, `tmpfs`, `labels`, `stop_signal`, `stop_grace_period`,
`pull_policy`; named volumes and networks of the file's own, with no driver options and no fixed
names; bind mounts only of files inside `app/` and only read-only. Anything else is refused by
name, including `privileged`, capabilities, devices, host namespaces, any host path, `env_file`,
`container_name`, `secrets`, `configs`, `include` and `extends`. A refused file starts nothing,
and every journey row fails. If you need something the check refuses, say so in your handoff
note; widening it is an exam change, which is the founder's.

## The exam, and how to run it

From the repository root: `sh eval/run.sh`. It needs Docker with Compose v2, Node.js 22 and
Python 3.12. In order, each step whatever happened to the one before:

1. **The conventions step** (`eval/conventions.sh`, TECH-SPEC section 14.1): pinned linters and a
   secret scan over `app/`.
2. **The API rows** (`eval/api/`), as in story 1.
3. **The browser rows** (`eval/web/`), against the exam's own stack (`eval/stack/compose.yml`),
   which builds `app/web` its own way; your `app/web/Dockerfile` is not used there.
4. **The journey rows** (`eval/e2e/`), against your stack, started as
   `docker compose -p <run>-app -f app/compose.yml --env-file eval/e2e/eval.env up -d --build --wait --wait-timeout 300`,
   so every service must be running, and healthy where it has a health check, within 300
   seconds. The rows reach it at `http://localhost:8080`. The three production rows, last, stop
   and start it with the same file, project and env file: `down -v` then
   `up -d --build --wait` (a first start: exactly the three seeded users), then twice `down` and
   `up -d` (every committed change is still there, and the users are not seeded again).

The reports land in `eval/reports/`, one case per row, the row id opening each case's name, and
the run ends with the row check: every id in `eval/api/rows.txt`, `eval/web/rows.txt` and
`eval/e2e/rows.txt` needs a passing case. A missing, failed, errored or skipped case fails it.
The production rows run only when every journey row has passed; until then they are reported as
skipped and counted as failing. What each row checks is in `docs/eval-plan.md` section 3. Open a
trace with `eval/web/node_modules/.bin/playwright show-trace <file>`.

The journey rows: T-001 P5 N8; T-003 P5 N5; T-004 P7 N9; T-005 N5 N7; T-006 P7; T-007 P4;
T-008 N11 N12; T-009 P5; T-010 P7; T-011 P7 N9; T-012 P5 P7 N10; T-013 P14 P17 P19 P22 P24 N5;
T-017 N3 N4. The production rows: T-016 P3 P4 N3.

The two human reviews of the blueprint (R1, the mockup comparison, and R2, the non-goal
walk-through) are not this story's and not the exam's.

## Done

`sh eval/run.sh` exits 0: the conventions step is clean and every row of all three lists passes;
the only files you changed are those `eval/stories/3.txt` allows; and `.pod/story-3/handoff.md`
says what you built, what passes, and anything you could not make pass and why. A test you
believe is wrong is reported there, never edited.
