# the API routes and start-up

Build the HTTP API of the Shared Equipment Checkout service so that the exam in `eval/api/`
passes: 55 rows, driven over the network against your application running in a container on a
real PostgreSQL 16.

## What exists and is not yours to change

`app/api/app/db.py` and `app/api/app/rules.py` are built: the schema, `make_engine(url)` and
`initialise(engine)` (creates the tables and seeds the three users, safe to run again), and the
pure rules layer: `Actor`, `Item`, the errors `Forbidden`, `Invalid`, `Conflict`,
`IdentityError`, and `parse_user_id`, `normalise_name`, `resolve_borrower`, `require_admin`,
`check_borrowable`, `check_return`, `check_delete`, `check_mark_out_of_service`,
`check_restore`. Read both files first; your routes call them and add no rule of their own.
`app/api/requirements.txt` already lists FastAPI, uvicorn, SQLAlchemy and psycopg.

## Your three files

- `app/api/app/config.py`: `load_settings(environ=None) -> Settings`, a frozen dataclass with
  one field `database_url`; `ConfigError` for a missing or malformed `DATABASE_URL`, naming the
  setting and never its value (blueprint 12.4).
- `app/api/app/routes.py`: the eight routes of blueprint 12.3 and nothing else.
- `app/api/app/main.py`: the FastAPI application `app`, the identity check outermost, and the
  lifespan start-up in this order: `load_settings`, `make_engine`, `initialise`, keep the engine
  on `app.state`; dispose on shutdown. Read no setting at import time. The exam runs you as
  `uvicorn app.main:app`.

## The contract, pinned in `docs/TECH-SPEC.md`

- **5.1 the acting identity.** The header `X-User-Id`: one header, one to nine ASCII digits,
  full match, naming a seeded user. Anything else, including no header, two headers, or a
  well-formed id nobody has, is refused with 403 and an empty body, before routing, for every
  method and every path. The rules layer's `parse_user_id` is the parser.
- **12.2 and 12.3** the resources, the eight routes, and every status each may answer, with the
  ledger 12.3.1 saying why. A carried-out action answers 200 with the item it acted on; the two
  listings answer their arrays, items by id ascending.
- **5.3** the order of checks for a valid request. **Section 8** one active loan per item under
  two simultaneous requests: a row lock, so the second request meets the state the first left.
- **5.4** the access log: one INFO record per request on the logger `app.access`, in the form
  section 5.4 states. No test reads it.
- **Non-goals.** No other routes, no CORS, no interactive documentation, no health route.

## The exam, and how to run it

From the repository root: `sh eval/run.sh`. It needs Docker. It builds your `app/api` into a
container (`eval/compose.yml` shows exactly how it is run), starts PostgreSQL, and runs every
row against it; the report lands in `eval/reports/api.xml`, one case per row, the row id opening
each case's name. What each row checks is in `docs/eval-plan.md` section 3, under its
requirement. No row reads a status code: a row knows an action was carried out because the
answer delivered the item and the list read back shows it, and knows it was refused because the
answer carried nothing and the list is unchanged.
